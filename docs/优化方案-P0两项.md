# P0 优化方案（两项）

> 对应体验评估报告《2026-10-14-用户体验评估》问题 1、问题 2。
> 均为前端（web/）改动，不涉及后端/数据库表结构变更。

---

## 方案一：会话失效无感知，全站仅显示「操作失败，请稍后重试」

### 1. 涉及功能 / 模块

| 模块 | 文件 | 职责 |
|------|------|------|
| 错误归一化 | `web/src/lib/unwrap.ts` | `unwrap` / `friendlyError` / `readCode` / `readKind` |
| 记录数据服务 | `web/src/services/recordService.ts` | 所有云端 CRUD（统一 `unwrap` 抛错） |
| AI 服务 | `web/src/services/aiService.ts` | 生成/总结/关联/交叉建议（走云 LLM + 回写） |
| 认证 | `web/src/services/authService.ts`、`web/src/store/authStore.ts` | 会话订阅、`setSession` |
| 启动引导 | `web/src/main.tsx` | 恢复会话、`onAuthStateChange` 订阅 |
| 登录页 | `web/src/pages/LoginPage.tsx` | 登录成功后 `navigate('/')` |
| 展示层 | `HomePage` / `RecordsPage` / `TodoPage` / `ReviewPage` / `SettingsPage` / `RecyclePage` | 各页 `friendlyError(err)` 后渲染文案 |

### 2. 当前问题与瓶颈（根因）

- **SDK 数据库 401 未归一化为「登录失效」**：SDK 仅在 auth 模块的 `normalizeHttpError` 里把 HTTP 401 映射为 `kind='unauthenticated'`（`errorKind(status, code)` 的 `case 401`）；而 `cloud.database.from('records')…` 走的是 PostgREST 风格路径，返回的 `error` 对象**既不是 `kind='unauthenticated'`，`code` 也不以 `auth_` 开头**。
- **兜底文案吞掉真实原因**：`friendlyError` 第 73 行 `if (message && !message.includes('{')) return message`——数据库 401 的 `message` 常含 JSON/花括号，被该条件过滤，最终落到第 74 行兜底「操作失败，请稍后重试」。
- **无跳登录动作**：`main.tsx` 已订阅 `onAuthStateChange`，`SIGNED_OUT` 时 `setSession(null)` 会触发 `RequireAuth` 跳 `/login`（这条链路是好的）；但数据库请求返回 401 **不会**触发 SDK 的 `SIGNED_OUT`，因此过期后页面停留在原地只显示笼统报错（实测首页/记录/待办/设置/回收站全部命中）。

### 3. 期望目标

1. 会话失效时，用户**被明确告知「登录已失效」并自动跳转登录页**，重登后回到原操作页面；
2. 错误文案按「登录失效 / 网络异常 / 服务不可用 / 参数错误 / 其他」**分类展示**，不再统一一句「操作失败」；
3. 瞬时网络/服务故障可**就地重试**。

### 4. 优化范围

- **改**：`web/src/lib/unwrap.ts`（新增错误分类）、`web/src/main.tsx`（注册全局拦截钩子）、`web/src/pages/LoginPage.tsx`（回跳）、`web/src/services/authExpired.ts`（新增）、各展示页补重试按钮。
- **不改**：`node_modules` 内 SDK 源码、后端 RLS/数据库、`cloud.ts` 单例、`authStore` 的数据结构。

### 5. 约束条件

- 不修改 SDK（升级 SDK 后仍兼容）；不碰 `owner_id` 由后端 `DEFAULT auth.uid()` 填充的安全边界。
- 兼容 Electron 桌面端（与 Web 同代码）与 `?mode=companion` 悬浮窗模式。
- 微信登录回调、token 自动刷新（`TOKEN_REFRESHED`）流程不被破坏；保留现有 `SIGNED_OUT` 链路。
- 前端绝不打印/透传 token、手机号；错误日志不含敏感信息。
- 不引入新依赖，复用现有 `zustand` / `react-router`。

### 6. 验收标准

- **单元测试**（`qa/` 新增 `errors.test.ts`）：`classifyError`/`isAuthExpired` 对 5 类错误对象（① `{status:401}` ② `{code:'401'}` ③ `{kind:'unauthenticated'}` ④ 网络 `{kind:'network'}` ⑤ 未知）返回正确类别；`friendlyError` 对应文案正确。
- **集成（真实浏览器，Edge headless + 注入伪造 token）**：任一云端页面（首页/记录/待办/设置/回收站）发起请求后，**自动跳转 `/login` 或弹「登录已失效」并跳转**，不再停在原地显示「操作失败」。
- **回跳**：从 `/records` 失效跳转登录 → 重登成功后回到 `/records`。
- **差异化**：断网显示「网络异常…」且可重试；服务端 500 显示「服务暂时不可用…」。
- **回归**：正常登录态下全功能不受影响；`typecheck` 0 报错、现有 220 用例全部通过。

### 7. 可执行方案

**步骤 A — 增强错误分类（`unwrap.ts`）**

新增两个纯函数（不改 `unwrap` 签名）：

```ts
export type ErrorClass = 'auth' | 'network' | 'server' | 'validation' | 'unknown'

export function isAuthExpired(err: unknown): boolean {
  const e = err as any
  if (!e) return false
  if (e.kind === 'unauthenticated') return true
  if (e.status === 401 || e.httpStatus === 401 || e.statusCode === 401) return true
  if (e.code === '401' || e.code === 'invalid_jwt' || e.code === 'session_not_found') return true
  const msg = String(e.message ?? '')
  return /401|expired|token.*(invalid|expired)|jwt/i.test(msg)
}

export function classifyError(err: unknown): ErrorClass {
  if (isAuthExpired(err)) return 'auth'
  const e = err as any
  const kind = e?.kind ?? ''
  if (kind === 'network' || /network|fetch|ECONN/i.test(String(e?.message ?? ''))) return 'network'
  const status = Number(e?.status ?? e?.statusCode ?? 0)
  if (status >= 500 || kind === 'backend-unavailable') return 'server'
  if (status === 400 || kind === 'invalid-request' || String(e?.code ?? '').startsWith('request_')) return 'validation'
  return 'unknown'
}
```

`friendlyError` 顶部优先走 `classifyError`：`auth → '登录已失效，请重新登录'`、`network → '网络异常，请检查网络后重试'`、`server → '服务暂时不可用，请稍后重试'`，其余保留现有分支。

**步骤 B — 新增全局拦截（`services/authExpired.ts`）**

```ts
import { useAuthStore } from '@/store/authStore'
import { isAuthExpired } from '@/lib/unwrap'

const REDIRECT_KEY = 'personal-agent.redirect-after-login'

export function reportAuthExpired(): void {
  if (!useAuthStore.getState().session) return          // 已登出，避免重复
  sessionStorage.setItem(REDIRECT_KEY, location.pathname + location.search)
  useAuthStore.getState().setSession(null)              // RequireAuth 自动跳 /login
}
export function consumeRedirect(): string | null {
  const v = sessionStorage.getItem(REDIRECT_KEY); sessionStorage.removeItem(REDIRECT_KEY); return v
}
export function onServiceError(err: unknown): void {
  if (isAuthExpired(err)) reportAuthExpired()
}
```

**步骤 C — 挂全局钩子（最小侵入，`unwrap.ts` + `main.tsx`）**

在 `unwrap.ts` 暴露一个模块级钩子，让所有 `unwrap({data,error})` 调用点自动获得 401 拦截，无需逐个改 service 方法：

```ts
let authHook: ((err: unknown) => void) | null = null
export function setUnwrapAuthHook(fn: ((err: unknown) => void) | null) { authHook = fn }
export function unwrap<T>(r: ResultEnvelope<T>): T {
  if (r.error) { authHook?.(r.error); throw r.error }
  return r.data as T
}
```

`main.tsx` 在 `bootstrap()` 内、渲染前调用：

```ts
import { setUnwrapAuthHook } from './lib/unwrap'
import { onServiceError } from './services/authExpired'
setUnwrapAuthHook(onServiceError)
```

> 注意：`aiService` 内部若有未走 `unwrap` 的裸 `error` 分支，也在其 catch 里补一行 `onServiceError(err)`。

**步骤 D — 登录成功回跳（`LoginPage.tsx`）**

`submit` 成功后：`navigate(consumeRedirect() ?? '/', { replace: true })`；微信回调路径在 `main.tsx` 里同样 `setSession` 后由 `RequireAuth` 生效（如需回跳同样读 `consumeRedirect()`）。

**步骤 E — 差异化 + 重试（与体验报告问题 4 同根，一次重构解决）**

`HomePage`/`RecordsPage`/`RecyclePage` 的错误区补「重试」按钮（复用思维树页 `handleRetry` 的交互模式）；`classifyError === 'network'` 时按钮文案为「重试」，`'auth'` 时不渲染重试（会跳登录）。

## 方案二：手动「新建树」是死胡同——根节点无法手动添加第一个思考点

### 1. 涉及功能 / 模块

| 模块 | 文件 | 职责 |
|------|------|------|
| 节点视图 | `web/src/components/mindtree/MindTreeNodeView.tsx` | 根/维度/思考点通用递归卡片，`isRoot` 分支（第 219–238 行）只渲染两个按钮 |
| 页面编排 | `web/src/pages/MindTreePage.tsx` | `handleAdd`（第 282–290 行）、`mutateTreeById`、树/树林操作 |
| 数据层 | `web/src/services/mindforest-store.ts` | `createNode`、`upsertTree`、`saveForestStore`（localStorage debounce 400ms） |
| 维度 | `web/src/components/mindtree/dimensions.ts` | `createNode`、`dimensionColor`、`dimensionLabel` |

### 2. 当前问题与瓶颈（根因）

- `MindTreeNodeView` 的 `isRoot`（`depth===0`）分支**只渲染**「重新生成全部分支 / 删除整棵树」两个按钮（第 219–238 行）；「添加一个思考点」（`PostAddIcon` → `setEditing('add')` → `onAdd`）**只存在于非根分支**（第 260–271 行）。
- 因此侧栏「新建树」产出的空树（根 `children=[]`）没有任何手输入口，只能依赖 AI 生成；AI 不可用/弱网时功能完全断链。
- `handleAdd` 本身是通用的（`updateTree(tr.root, node.id, …)` 命中 `root.id` 即可 `push`），**数据层无需改动**，纯粹是 UI 入口缺失。

### 3. 期望目标

- 新建空树后，根卡片即可**手动录入第一个思考点**，不依赖 AI；
- 与子节点「添加一个思考点」的交互完全一致（内联输入、Enter 提交、Escape/取消）；
- 手动节点正常持久化（刷新仍在）且不与 5 维度 AI 分支、交叉关联冲突。

### 4. 优化范围

- **改**：`MindTreeNodeView.tsx`（根分支补入口）、`MindTreePage.tsx`（可选：根按钮布局优化）。
- **不改**：`mindforest-store.ts` 数据模型、`createNode`、交叉关联逻辑、localStorage 存储格式。

### 5. 约束条件

- 手动添加的节点**不带 dimension**，沿用现有渲染：`node.dimension && <Chip/>` 不渲染维度 Chip、`dimensionColor` 落到 `theme.palette.divider`——保持现状即可，不引入新数据字段（避免破坏 v2.7.0 存储结构）。
- 交叉关联按节点 `id` 与文本匹配，与维度无关，不受影响。
- `node.loading` 期间禁用新增按钮，避免与 AI 流式写回竞态。
- 兼容桌面端：继续用内联输入框，禁止 `window.prompt`。
- 不新增 localStorage 版本迁移；存储格式 `personal-agent.mindforest.v1` 不变。

### 6. 验收标准

- **交互**：新建空树 → 根卡片出现「添加一个思考点」入口 → 点击弹出内联输入（`autoFocus`）→ Enter 提交 → 节点即时出现在 5 维度 Grid（无维度样式，中性灰）→ **刷新后节点仍在**。
- **一致性**：根入口与子节点行为一致（Enter 提交 / Escape 取消 / 「确定」「取消」按钮）。
- **回归**：AI「生成思维树」「重新生成全部分支」「就这一点深挖」「删除节点/整树」「手写」全部不受影响；两棵树以上交叉关联与树林流程不变。
- **测试**：`qa/mindforest-store.test.ts` 增补「根节点手动 add 子节点」用例；`typecheck` 0 报错、现有用例全绿。

### 7. 可执行方案

**步骤 A — 根分支补「添加一个思考点」入口（`MindTreeNodeView.tsx` 第 219–238 行）**

在 `isRoot` 分支的「重新生成全部分支」之前插入一个与子节点同款的 `IconButton`：

```tsx
{isRoot ? (
  <>
    <Tooltip title="添加一个思考点">
      <IconButton
        size="small"
        onClick={() => { setDraft(''); setEditing((v) => (v === 'add' ? null : 'add')) }}
        disabled={node.loading}
      >
        <PostAddIcon fontSize="small" />
      </IconButton>
    </Tooltip>
    <Button size="small" startIcon={<RefreshIcon />} onClick={() => onRegenerate(node)} disabled={node.loading}>
      重新生成全部分支
    </Button>
    <Button size="small" color="error" startIcon={<DeleteIcon />} onClick={() => onDelete(node)} disabled={node.loading}>
      删除整棵树
    </Button>
  </>
) : ( … )}
```

内联输入框（第 311–332 行）已支持 `editing==='add'`，无需改动；`submitEditing` 里 `if (editing === 'add') onAdd(node, text)` 直接复用。

**步骤 B — 确认 `handleAdd` 对根节点生效（`MindTreePage.tsx` 第 282–290 行）**

现有实现 `updateTree(tr.root, node.id, (n) => ({ ...n, children: [...n.children, createNode(t)] }))` 对 `node.id === root.id` 同样成立（`updateTree` 第 71 行 `if (root.id === targetId) return updater(root)`），**无需改动**；仅需在 `MindTreeNodeView` 根节点也传入 `onAdd`（页面已传，第 501 行）。

**步骤 C — 根卡片按钮布局微调（可选）**

空树时「重新生成全部分支」文案易误解为「必须 AI」；建议空树（`!hasChildren`）时该按钮文案改为「AI 生成分支」、有分支时保持「重新生成全部分支」，并给按钮组加 `flexWrap:'wrap'` 避免窄屏换行错位。

**步骤 D — 测试兜底**

在 `qa/mindforest-store.test.ts` 增加纯函数级用例：对 `{root:{id:'r',children:[]}}` 调用与 `handleAdd` 等价的 `updateTree(root,'r',n=>({...n,children:[...n.children,createNode('x')]}))`，断言 `children.length===1` 且新节点 `dimension===undefined`。
