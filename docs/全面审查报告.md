## 一、总体结论

由产品经理（许清楚）、工程师（寇豆码）、QA（严过关）三方并行独立审查，覆盖 8 个维度，**去重后共 40 项问题**：

| 优先级 | 数量 | 含义 |
| --- | --- | --- |
| **P0** | 1 | 严重/阻塞，核心功能不可用 |
| **P1** | 8 | 重要，需尽快修复 |
| **P2** | 20 | 优化，建议排期处理 |
| **P3** | 11 | 低优先，可后续迭代 |

**最需要关注的三件事：**

1. **P0 — VS 代码分析链路是「断头路」**：桌面读码后推送的 `evtVsStarted` 事件渲染层无人订阅，产品核心卖点「VS 启动 → 读码 → 分析 → 推送优化建议」实际不工作。
2. **P1（安全）— IPC 边界无来源/入参校验**：主窗口/悬浮窗加载远程 Web，`window.desktopBridge` 暴露的特权能力（spawn 本地进程、读剪贴板、枚举磁盘）可被远程页面调用，一旦远程站被 XSS 即构成本地任意代码执行。
3. **P1（体验）— 多处「半成品」**：昵称/头像只在设置页生效、相关记录点不动、重新生成摘要不刷新、清除搜索无效。

## 二、问题清单

### P0（严重/阻塞）

#### 1. VS 代码分析链路断头：`evtVsStarted` 无人订阅，状态永远卡在「分析中…」
- **维度**：功能完整性
- **位置**：`desktop/src/main/analysis-orchestrator.ts:104-142`（成功读码后发 `evtVsStarted` 并置 `analyzing=true`，仅 catch 分支复位）；`desktop/src/main/ipc.ts:89`；`web/src/components/CompanionPanel.tsx`（只订阅 `onStatusChanged/onSelectionRead/onFloatingWindowStateChanged`，无 `onVsStarted`）
- **影响**：产品核心卖点「VS 启动→读码→LLM 分析→推送建议」实际不工作；读到的源码（含内容）发出后无人订阅，`analysisDone` 不回传，悬浮窗永久「分析中…」，VSIX 导出永不执行。
- **建议**：在 `CompanionPanel` 订阅 `bridge.onVsStarted` → 调 `aiService` 分析 changedFiles → 回传 `bridge.analysisDone`；若该能力已下线，则移除 vs-monitor / solution-reader / analysis-orchestrator / analysis-exporter 残留，避免「半成品管线」误导。

### P1（重要）

#### 2. IPC 边界无运行时来源/入参校验（安全）
- **维度**：稳定性 / 安全
- **位置**：`desktop/src/main/ipc.ts:132-141`（cppCompile/cppRun/cppDebugStart）、`:73`（readSelection）、`:75-85`（getLocalPaths/setExportDir）；`desktop/src/main/cpp-runner.ts:173-175`（`spawn(binaryPath)` 无路径校验）
- **影响**：主窗口/悬浮窗加载远程 Web（`https://your-app.workbuddy.host`），bridge 暴露的特权能力可被远程页面调用；远程站被 XSS 即可 spawn 任意本地 exe、任意时刻读剪贴板、枚举磁盘路径。
- **建议**：`cppRun/cppDebugStart` 的 binaryPath/sourcePath 强制解析并校验在 `CPP_TMP_DIR` 内；`cppCompile` 源文本加长度上限；`setExportDir` 加长度/非法字符校验；特权 handler 统一校验 `event.sender`；`readSelection` 改为仅快捷键触发（不经 renderer 任意拉取）。

#### 3. 悬浮窗自动收起 suspend/resume 配对缺陷
- **维度**：稳定性
- **位置**：`desktop/src/main/analysis-orchestrator.ts:95-143`
- **影响**：`suspendFloatingAutoCollapse()` 后多条提前 return / 抛错分支不调用 `resume`，一旦命中 `floating-window` 的 suspended 永久为 true，自动收起静默失效。
- **建议**：suspend 移到确认进入分析（win 就绪且 codeUploadEnabled=true）之后；或将 resume 抽成 `try/finally` 包裹整段，保证所有出口恢复。

#### 4. VS 探测每 3s 反复 spawn PowerShell + 重复编译 Add-Type
- **维度**：性能
- **位置**：`desktop/src/main/vs-monitor.ts:138-199`（poll）、`:69-86`（detectForegroundPid）
- **影响**：每 3 秒一次 powershell spawn；VS 打开时每 3s 跑 `detectForegroundPid`（内嵌 Add-Type 编译 C# 且不缓存），长期运行持续占用主进程 CPU/进程创建。
- **建议**：Add-Type 编译结果缓存复用；VS 未运行时探测退避到 10~15s；`detectForegroundPid` 结果节流。

#### 5. 搜索结果「清除搜索」按钮无效
- **维度**：交互体验
- **位置**：`web/src/pages/RecordsPage.tsx:79-88`
- **影响**：用 `window.history.replaceState` 改 URL，但组件关键词来自 `useSearchParams`，replaceState 不触发 React Router 更新，页面不重渲染，搜索结果残留。
- **建议**：改用 `navigate`/`setSearchParams` 删除 keyword，或直接 `setFilter({ keyword: undefined, page: 1 })` 触发 reload。

#### 6. 详情弹窗「重新生成摘要」后界面不更新
- **维度**：交互体验
- **位置**：`web/src/components/RecordDetail.tsx:92-102`；`web/src/pages/HomePage.tsx:132-138`、`RecordsPage.tsx:131-137`（onChanged={load} 只刷新列表，不更新 detail 对象）
- **影响**：重新生成摘要后弹窗仍显示旧摘要，需关闭重开才可见。
- **建议**：regenerateSummary 成功后用返回的 InfoRecord 更新父级 detail state，或让 RecordDetail 本地保存最新 summary。

#### 7. 详情弹窗「相关记录」点不动
- **维度**：功能完整性
- **位置**：`web/src/components/RecordDetail.tsx:262`（`<RelatedRecords sourceId={record.id} />` 未传 onSelect）；`web/src/components/RelatedRecords.tsx:69-72`
- **影响**：「智能关联」只展示不可跳转，用户无法从相关记录打开目标，功能只做了一半。
- **建议**：RecordDetail 传入 `onSelect` 打开目标记录（替换当前 record），形成关联浏览闭环。

#### 8. 启动等待界面无超时兜底
- **维度**：稳定性 / 交互
- **位置**：`web/src/components/BootScreen.tsx`（纯静态）；`web/src/main.tsx` bootstrap()（无超时/重试）
- **影响**：会话恢复/网络卡住时「正在加载…」永不结束。
- **建议**：BootScreen 增加 10s 超时态 + 「重试」按钮（重新触发 bootstrap），失败展示可读错误文案。

#### 9. 昵称/头像只在设置页生效，顶栏未同步
- **维度**：功能完整性
- **位置**：`web/src/components/Layout.tsx:190`（userLabel 只取 user.name/phone/email）、`:243-246`（Avatar 仅首字）；`web/src/pages/SettingsPage.tsx` 已存 nickname/avatar
- **影响**：v2.9.x 新增昵称/头像是「半成品」，只在设置页可见，顶栏头像/用户名仍走旧逻辑，用户改完看不到全局生效。
- **建议**：全局统一读昵称/头像（authStore 或独立 profile store 缓存），Layout 顶栏优先展示昵称与头像。

### P2（优化）

#### 10. 顶栏「导出」仅当前页 + Layout 订阅 records 导致整壳重渲染（合并 PM + 工程师）
- **维度**：功能完整性 / 性能
- **位置**：`web/src/components/Layout.tsx:109、161-171`
- **影响**：非记录页点导出可能导出空/过期数据，记录页也只导出当前页 ≤20 条（数据丢失错觉）；同时 Layout 订阅 records 用于导出，列表每次变化都重渲染整个 AppBar/Drawer。
- **建议**：导出改用 `useRecordStore.getState()` 或专用 `exportAll` 服务拉全量（分页循环/高 limit）并明确文案；移除组件级 records 订阅。

#### 11. 检索 keyword 未转义 → PostgREST 过滤器注入（合并 QA + 工程师）
- **维度**：缺陷风险 / 安全
- **位置**：`web/src/services/recordService.ts:124、198、308`
- **影响**：`query.or(\`title.ilike.%${kw}%,content.ilike.%${kw}%\`)` 把用户输入直拼进过滤串；kw 含 `,`/`(`/`)`/`%`/`_` 时可注入额外过滤条件或致查询报错（RLS 仍按 owner_id 隔离不越权，但破坏同权限范围查询语义）。
- **建议**：转义 `%/_/\,()"`，或改用 SDK 参数化 `ilike` 分列 AND/OR，避免手拼 `or` 字符串。

#### 12. 图片对象一致性缺陷（上传孤儿对象 / 删除脏记录）
- **维度**：稳定性
- **位置**：`web/src/services/imageService.ts:96-104`（回滚只删 DB 占位行，不删已上传对象）；`:133-142`（deleteImage 先删对象、对象删除失败即抛错致记录残留）
- **影响**：缩略图上传中途失败 → 已传对象永久占用云存储（泄漏）；删除时对象删除失败 → 记录残留指向不存在对象（死图）。
- **建议**：上传失败时按「已成功上传路径」反向 best-effort 删对象；deleteImage 改为「先删库、后删对象」，对象清理失败仅告警不阻断，或引入后台孤儿对象清理任务。

#### 13. friendlyError 泄漏原始后端 message
- **维度**：稳定性 / 安全
- **位置**：`web/src/lib/unwrap.ts:125`（`if (message && !message.includes('{')) return message`）
- **影响**：不含 `{` 的原始 error.message 原样透传，可能暴露表名/字段名/后端细节，违背同文件头「不暴露后端堆栈与敏感信息」约定。
- **建议**：白名单放行项目内已知中文文案，其余统一落为「操作失败，请稍后重试」；或对 message 做脱敏（去路径/表名/引号内容）。

#### 14. recordStore.load 无请求序号，存在竞态
- **维度**：稳定性
- **位置**：`web/src/store/recordStore.ts:38-47`
- **影响**：快速切换分类/翻页/搜索时两个 listRecords 并发，较慢旧请求后返回覆盖新结果（显示错误页数据）。
- **建议**：load() 内自增 requestId，响应返回时仅当仍是当前 requestId 才 set。

#### 15. readSolution 全同步读取，阻塞 Electron 主进程
- **维度**：性能
- **位置**：`desktop/src/main/solution-reader.ts:82-150`（readFileSync/readdirSync/statSync + 递归）；由 `analysis-orchestrator.ts:119` 同步调用
- **影响**：VS 启动事件触发主进程同步递归读文件+哈希，大解决方案下主进程卡顿（托盘/悬浮窗/全局快捷键无响应）。
- **建议**：移入 worker_threads 或改异步 fs（promisify），完成后 IPC 回推；或至少 setImmediate 分片。

#### 16. analyzeScreenshot 用 `as any` 绕过类型，且绕过模型缓存
- **维度**：代码质量
- **位置**：`web/src/services/aiService.ts:481-494`
- **影响**：`(cloud.llm.chat.completions.create as any)` 破坏类型安全；直接 `models.list()` 而非复用 `getModelId`/缓存，多模态模型选择逻辑散落不一致。
- **建议**：定义局部窄类型或扩展 SDK 类型；多模态模型选择抽成 `getModelId('vision')` 复用缓存。

#### 17. recordService 十余处重复「unwrap + 判空抛错」样板
- **维度**：可维护性
- **位置**：`web/src/services/recordService.ts:103-104,128-130,185,203,217-218,240-241,253-254,264-265,275-276,286-287,297-298,313-314` 等
- **影响**：`unwrap(...) as RecordsRow[]|null; if(!rows?.length) throw ...` 模式重复约 12 次，改一处需改全量，易漏。
- **建议**：抽 `unwrapRows(result, msg?)` / `requireRow(result)` 私有助手统一「解包+空值抛错+映射」。

#### 18. 设置双源（云 settings vs 桌面 preferences.json）仅部分桥接
- **维度**：可维护性
- **位置**：`desktop/src/main/store.ts:12-34` 与 `web/src/pages/SettingsPage.tsx`
- **影响**：vsPath/codeUploadEnabled/floatWindowEnabled/notifyEnabled 同时存于云 settings 与本地 preferences.json；仅 codeUploadEnabled 走 bridge 同步，vsPath 存云后本地无同步路径（vs-monitor 也未消费 vsPath），存在两端分叉/设置不生效隐患。
- **建议**：明确每项设置权威源（云端=跨端，本地=设备偏好），为需同步字段补 bridge，或云端为唯一源、本地只读缓存。

#### 19. aiService 魔法值散落、无集中配置
- **维度**：可维护性
- **位置**：`web/src/services/aiService.ts`（4000/6000/16000/30000/12000 截断、10/20/5/50/8/3 条数、200 节点、250ms 节流）、`recordService.ts`（500/200 条）、`mindforest-cross.ts`（200/80）
- **影响**：截断长度与结果条数语义耦合在业务代码里，调整需多处翻找，易不一致。
- **建议**：集中到 `shared/config` 或模块顶部常量（LLM_INPUT_LIMITS、RESULT_LIMITS），按用途命名注释。

#### 20. getModelId 模型缓存无 TTL
- **维度**：稳定性
- **位置**：`web/src/services/aiService.ts:37-103`
- **影响**：cachedModels 命中后永久有效（除非 setAnalysisPreference 或刷新）；云端模型被禁用后会持续用失效 id 报错直到刷新。
- **建议**：缓存加时间戳 TTL（10~30min），或监听错误码触发 clear 重取。

#### 21. LLM 调用无并发去重与取消
- **维度**：性能

- **位置**：`desktop/src/main/store.ts:33`、`desktop/src/main/analysis-orchestrator.ts:34`
- **影响**：cache 每个 solutionPath 永久累积、lastTriggerAt 永不清理，preferences.json 膨胀。
- **建议**：cache 加 LRU 上限（如最近 50 方案）；lastTriggerAt 定期清理过期项。

#### 34. RecordsPage 类型不安全 cast 与 mount 双重加载
- **位置**：`web/src/pages/RecordsPage.tsx:31、44-50`；`HomePage.tsx:62-68`
- **影响**：`params.get('type') as RecordType` 未校验（`?type=garbage` 透传）；setFilter+load 两个 effect 在 mount 可能双请求。
- **建议**：校验 type 枚举否则回退 undefined；合并为单一 effect 避免双触发。

#### 35. cpp-runner 临时文件无 per-run 清理
- **位置**：`desktop/src/main/cpp-runner.ts:107-122、172-190`
- **影响**：每次编译随机 .cpp/.exe 落 tmpdir，仅 before-quit dispose 清理，长期积累磁盘垃圾。
- **建议**：编译/运行成功即清 source/binary（或保留最后 N 个），失败产物短 TTL 清理。

#### 36. 导航徽标每次路由变化 4 次 count 查询
- **位置**：`web/src/components/Layout.tsx:120-133`
- **影响**：counts() 内部 4 条 count 查询，依赖 pathname，每次切页重查无缓存/防抖。
- **建议**：结果 30~60s 缓存，或改「记录增删后失效」事件驱动刷新。

#### 37. updateService.checkForUpdate 无超时
- **位置**：`web/src/services/updateService.ts:55`
- **影响**：更新源挂起时检查永久 pending，手动按钮一直转圈。
- **建议**：加 AbortController 超时（如 8s）。

#### 38. isAuthExpired 的 message 正则存在误判
- **位置**：`web/src/lib/unwrap.ts:69`
- **影响**：合法第三方错误文案含 "expired"/"401" 会误判为会话失效，触发误登出+回跳。
- **建议**：去掉 message 正则，仅依赖结构化字段（status/statusCode/httpStatus/code/kind），已覆盖主流 SDK 形态。

#### 39. 材料附件白名单含 svg（条件性 XSS）
- **位置**：`web/src/services/storageService.ts:7`
- **影响**：用户上传 SVG 可内嵌 `<script>`；若签名 URL 被新标签/同源直接打开存在脚本执行风险（`<img>` 场景安全）。
- **建议**：从白名单移除 svg，或强制 `content-disposition: attachment`、禁止内联打开。

#### 40. 测试覆盖缺口（高价值低成本补测点）
- **位置**：`qa/`（现有 242 用例）
- **缺口**：① recordService 的 createRecord/updateRecord/patchRecord/softDelete/restore/hardDelete/updateTodoStatus/search/stats/counts/listRelated/saveLinks 无单测（仅 listByRange 有）；② authService 无单测；③ storageService 无单测；④ aiService 的 classify/summarize/relate/answer/analyzeScreenshot/generateCode 无单测。
- **建议**：优先补 recordService CRUD/search 链（`qa/mocks/cloud.ts` 的 database mock 已就绪，参照 listByRange 低成本扩展）+ aiService classify/summarize 结构化解析；另补 recordStore.load 竞态回归测试。
