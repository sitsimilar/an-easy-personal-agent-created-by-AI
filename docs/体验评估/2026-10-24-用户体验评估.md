## 二、问题清单

> 已修复项不再重复列改进建议，统一在第三节「与上期对比」呈现。本节聚焦本期仍遗留的问题与新增问题。

### 问题 1：思维树数据仍仅存本机，无云端同步（上期问题 1 的遗留）

- **问题描述**：`personal-agent.mindforest.v1` 仍只写在浏览器 localStorage（`services/mindforest-store.ts` 的 `loadForestStore`/`saveForestStore` 均直接读写 `localStorage`，页面注释亦明示「思维树仅存本地，需手动搬运」）。「导出 JSON / 导入 JSON」已在上期落地作为手动备份/迁移手段，但换设备、清浏览器缓存、Web 端与桌面端之间仍无法自动同步，一旦忘记手动导出即丢失且不可恢复。
- **影响程度**：中
- **改进建议**：中期复用现有云库，新增 `mind_trees` 表（或并入 `settings`），实现「本地缓存 + 登录后云端同步」；同步策略建议：登录后拉取云端版本做合并/覆盖提示，本地写入防抖后推送云端。导出/导入 JSON 保留作为离线兜底。学习目标管理台已走通「资料库在线存储 + 多端同步」链路，可作为同一技术路径复用。
- **优先级**：P1 —— 数据丢失是用户最不能容忍的问题；现有云库基础设施可复用，改造成本可控，且这是「数据云端隔离存储」产品承诺对思维树的唯一缺口。
- **预期改进效果**：思维树跨设备一致、可恢复；「数据云端隔离存储」承诺对全部数据成立。

### 问题 2：`.host` 旧域名站点「检查更新」因 CORS 跨域静默失败（本期新增）

- **问题描述**：本次实测所有页面均持续抛出 `Access to fetch at 'https://personal-agent-08495.app.workbuddy.link/version.json' from origin 'https://personal-agent-08495.app.workbuddy.host' has been blocked by CORS policy`。经源码核对：`updateService.ts` 的更新源 `UPDATE_SOURCE_URL = ${publicConfig.endpoint}/version.json`，而 `publicConfig.endpoint` 来自构建时注入的 `VITE_CLOUD_ENDPOINT`（本地 `web/.env` 已切至 `.link`）。即 `.host` 域名上仍部署着「切换域名后」构建的产物（其 JS 内 endpoint 已指向 `.link`），但 `.host` 域名本身仍在对外服务（`curl .host/version.json` 返回 200），于是页面运行时向 `.link` 发起跨域请求，被 CORS 策略拦截。结果是「检查更新」功能静默失效（当前版本号仍能正常显示，因其为构建时注入常量）。
- **影响程度**：中
- **改进建议**：
  1. **首要**：确认正式域名已统一为 `.link`，让 `.host` 旧域名停止对外服务（下线或 301 永久重定向到 `.link`），避免用户停留在旧域名上遇到各类跨域/资源异常；
  2. **兜底**：`version.json` 请求改为「同源相对路径」（`/version.json`）而非依赖 `endpoint` 拼接，从根本上消除跨域；或由部署层 `server.js` 在返回 `version.json` 时显式补充 `Access-Control-Allow-Origin` 头；
  3. 评估脚本 `qa/ux-walkthrough.cjs` / `qa/ux-mindtree.cjs` 中的 `BASE` 常量应同步切换到正式域名 `.link`，避免长期针对旧域名走查得出误导性结论。
- **优先级**：P1 —— 虽然正式域名已切 `.link`，但只要 `.host` 仍可访问，任何通过旧链接/旧收藏/旧分享进入的用户都会遇到更新检测失效，且同源跨域问题可能波及其它依赖 `endpoint` 的请求；属于「域名切换未收尾」的线上卫生问题，应尽快收口。
- **预期改进效果**：旧域名不再产生跨域报错；更新检测在任意入口下均可正常工作；评估基线回归真实线上域名。

### 问题 3：思维树「导入 JSON」仍缺二次确认（上期问题 4 的遗留）

- **问题描述**：导入 JSON 的 Tooltip 已提示「会覆盖当前数据」，但仍未在导入前弹出二次确认对话框。用户误点导入（或选错文件）会直接清空现有树林；且导入文件为任意 JSON 时依赖 `deserializeForestStore` 校验，校验失败虽会提示「导入失败」，但覆盖行为发生在校验通过之后，一旦选错合法但内容不同的备份文件即不可逆。
- **影响程度**：低
- **改进建议**：导入前弹出确认对话框，明确列出「将覆盖当前 N 棵树 / M 个树林」；导入成功后支持「撤销导入」或先自动备份当前数据到 `BACKUP_KEY`（`mindforest-store.ts` 已有 `.bak` 备份机制可复用）。
- **优先级**：P3 —— 数据安全细节，配合问题 1 的云端同步落地前尤为必要。
- **预期改进效果**：避免误导入导致的数据覆盖丢失，提升数据安全感。

### 问题 4：会话失效拦截建议用「真实过期 token」补充验证（上期问题 2 的遗留）

- **问题描述**：源码层面会话失效链路完整（`main.tsx` 注册 `setUnwrapAuthHook(onServiceError)` → `unwrap` 抛错前回调 → `isAuthExpired` 识别 → `reportAuthExpired` 清会话跳登录 → `LoginPage` 消费回跳路径）。但本次评估注入的测试会话仍使用伪 token（`ux-eval-fake-token-not-real`），实测首页/记录/待办/设置/回收站命中 401 后页面仍显示「操作失败，请稍后重试」并**未触发跳转登录**。这可能是评估脚本伪 token 触发的 401 错误结构与真实 SDK 返回结构不一致所致，但存在「真实 token 过期场景拦截未生效」的回归风险，无法仅凭源码断言。
- **影响程度**：中（潜在）
- **改进建议**：补充一次「真实登录 → 手动使 token 失效（或等待过期）→ 刷新页面」的端到端验证，确认 `isAuthExpired` 能正确识别真实 SDK 的 401 结构并触发跳转；若未触发，则补齐对应错误字段到 `isAuthExpired` 的识别分支。
- **优先级**：P1 —— 会话失效是必现场景，是上期 P0 问题的修复验证，务必确认修复真实生效而非仅源码存在。
- **预期改进效果**：确认会话过期时用户一步完成重登并回到原操作现场，彻底消除「软件坏了」类困惑。
